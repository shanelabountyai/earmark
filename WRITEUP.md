# Earmark — write-up: one person, many tenants, one control

Build-log #23. A synthetic marketing budget and agency-spend governance tool (fiscal-month budgets, approval chains as data, POs, invoice matching, variance with replan markers, an AI variance explainer under a spend cap) sold to several client companies at once. Built on saas-foundation v1.5.0, upgraded to v1.6.0 before any table existed and v1.6.1 after, in six phases from 2026-11-04 to 2026-11-10. PRs #1–#4 merged; #5 (enterprise wiring) open, waiting only on two manual sign-ins. Demo: `docs/DEMO.md`. Decisions: `prd-earmark.md` §0 (D-01..D-37).

> Learning project, synthetic data only. Northwind, Contoso, Meridian, Dana and every budget, PO and invoice are generated by `scripts/seed-earmark.ts`. Emails use `.demo.test`. Not deployed. The SSO identity providers are test apps (Google, Okta); the e2e signs in through a mock IdP. Webhooks are delivered to a receiver inside the same app. The AI explainer runs on a stub unless a key is set. "Isolated" in this write-up means: the tests named below pass, under row-level security in enforce mode. It does not mean audited.

## The angle

Every earlier clone had one user in one tenant at a time. Earmark's hard user is **Dana**, an agency account manager who is a guest in two competing clients' orgs. She must see her own agency's POs inside Northwind, her own inside Contoso, and nothing else from either — not the budget behind the PO, not the other agency in the same client, not the other client.

So this was the first saas-foundation clone to run **Postgres row-level security in enforce mode from the first migration** (D-08). No off-mode phase to turn on later against code that assumed it was off.

The product exists to enforce one control: **no spend without a prior approval**. A commitment exists only for an approved request, for no more than it asked; an invoice matches a commitment, never a budget line (D-05). The method was to enforce that control three times, each layer unaware of the others:

1. **Pure engines, checked against Python.** `src/lib/earmark/{money,chain,rollup,match,variance}.ts`: `BigInt` cents, no database, no clock. Four stdlib-Python oracles in `tools/` compute the same answers from 132 hand-written fixtures, including every threshold boundary ($9,999.99 vs $10,000.00). Parity is 100 %, and the engines need ≥ 95 % coverage to pass CI (D-09).
2. **One door for writes.** Every Earmark action goes through `orgAction`, resolves every id before validating anything (so a foreign id is always the same 404 as a missing one), and checks Earmark's own permission or seat first (D-15, D-19).
3. **The database refuses it too.** A trigger refuses a `Commitment` whose request is not approved or that exceeds it; `CHECK`s keep money positive. Children reference their parent by `(id, orgId)`, because **a foreign-key check bypasses RLS**: a single-column FK would let a bug link one client's commitment to another client's request, and the composite key makes that impossible (D-13, D-19).

## What stands in the way of each failure

| Failure | Defense | Proof |
|---|---|---|
| Dana reads another client's PO by id | RLS enforce plus `inOrg` on every query; cross-org returns the same 404 as a missing id | Foundation INV-01..41 green under enforce; e2e step 8 (URL and API, identical 404 bodies) |
| Dana reads the other agency's PO in the same client | `GuestMembership(orgId, userId, agencyId)`; `scopeOf` fails closed, so a guest with no agency row sees nothing (D-12, D-29) | E-INV-03: byte-identical 404 for the other agency's id and a nonexistent one |
| A guest sees the budget behind the PO | `toGuestCommitment()` is an allowlist projection, used by the page and the API both (D-33) | E-INV-04: a dummy field added to the row does not appear |
| A requester approves their own request | The chain engine refuses self-approval through any seat held; the seed makes it real (`member@` holds Demand Gen Owner) | E-INV-01; e2e step 4 |
| A commitment without an approval | Engine, action and a database trigger (D-19) | E-INV-02, including a direct insert attempt |
| One invoice matched twice at the same moment | Lock the invoice row, then the PO; only `matchInvoice` takes both, so the fixed order cannot deadlock (`bf1d5ab`) | Concurrent-match test: red 3/3 before, green 3/3 after |
| A threshold edited mid-request | Rules are a row, edited with a before/after audit; in-flight requests keep their `chainSnapshot` (D-14) | E-INV-06 |
| An offboarded agency keeps access | One transaction marks the agency and closes its POs, so guests see nothing from that moment; removal is retry-safe (D-19, D-36) | E-INV-07; e2e step 13: Dana loses Contoso, keeps Northwind |
| The API and the guest form disagree on an invoice | Both call `fileInvoice` in `src/earmark/core.ts`: same rules by construction (D-33) | `api.test.ts`; e2e step 8 |
| The AI explainer runs up a bill | The foundation's `withBudget` cap; the fourth draft against a $1.00 cap is refused and writes nothing (D-35) | E-INV-08; e2e step 10 (three usage rows, then refused) |
| Floating-point drift in a variance report | Integer cents end to end, half-away-from-zero ratios | fast-check: cents arithmetic never yields a non-integer |

## What the method cost, and what it bought

Six template patches, each excused by its diff hash in `FOUNDATION_PATCHES.md`, because the template had no seam for a new role, a clone env var, or a cross-org cron. Three of them exist only for the `guest` role. A live demo that needs a real SSO owner promoted by one `psql` line (D-37), because the template refuses keys, exports and member removal to its shared demo accounts, on purpose. Requests, matches and the demo seed all run through the engines (D-20), so the seed is slower to write but cannot show a state the app could never reach.

What it bought: the gate at the end is lint, typecheck, `foundation:drift` clean, unit 523 + 1 skipped, and e2e 27/27 twice back to back against a production build, under RLS enforce. Every demo step that is automatable is in the e2e.

## What it does not do, stated

Not deployed. No real money, AP system or ERP. No rename or delete of plan rows, and no fiscal-year close with carry-forward: nothing sets `lockedAt` yet (D-26). No separation of duties between the person who matches an invoice and the one who approves it for payment (D-25). A guest is not bound to an agency automatically: an admin ties them after invite (D-29). The explainer's quality on real budgets was never measured; the demo counts drafts on a stub, because Haiku is too cheap to hit the cap in four (D-35). The Google and Okta sign-ins are verified by hand, once, not in CI.

## Found while building (the honest list)

- **`bf1d5ab` — a $1,000 invoice became $2,000 of actuals.** The over-match check read the invoice's existing matches without a lock, so two concurrent matches of one invoice against two POs both passed. Every single-threaded test was green. Found by a side review; failing test first.
- **D-23 — closing a PO un-spent its money.** The rollup counted open POs only, so closing one dropped its billed amount back into *available*: Q2 Paid Social showed its full $225,000 available after $18,000 had been billed. The engine and the Python oracle shared the rule, so parity could not catch it. The dashboard on real seed data did.
- **D-32 — Require SSO locked Dana out of everything.** The template refused a magic link to any member of an SSO-required org. Both demo orgs require SSO and Dana is in both, so she could not sign in at all. Agency staff are not on the client's IdP; guests are now exempt, staff still are not.
- **D-36 — offboarding could strand guests forever.** It marked the agency, then removed guests one by one; one refused removal left guests in the org, and every retry was refused as "already offboarded". Now refused up front for demo sessions, and a rerun finishes the job.
- **D-19 — the database had to enforce what the app already did.** Defence in depth for the one control the product exists for. The composite-FK rule came from noticing that an FK check reads across RLS.
- **`90dfb23` — CI red for five hours.** From the webhooks commit (`db9163e`) on, the template's modules-removed CI job stripped `sso` and `apikeys`, which Earmark depends on but had never declared required. One line in `src/app/required-modules.ts`. The local gate never runs that job; only CI does.
- **Template `ci.yml`** hardcodes `saas_foundation_test` in the enforce step, so every clone that turns on `RLS_ENFORCE=1` starts red. Fixed locally (`d1db748`); the template needs it.

Upstream to saas-foundation (v1.7.0): a `guest` role holding no core permission; the Require-SSO guest exemption; `ANTHROPIC_API_KEY` in `env.ts`; drift should exempt lines under `// clone entries below` in `cross-org.ts`; an invite-accept hook; the `ci.yml` database name.
